# Architecture — DYPOL Creator Console

## Design goals

1. Zero cost on genuine free tiers.
2. Heavy work (video rendering) never runs in the dashboard backend.
3. The dashboard is an **orchestrator + source of truth**, not a renderer.
4. Credentials never leave server-side secret storage.

## Why these choices

* **Cloudflare Pages + Functions + D1** — one free platform for static SPA,
  API and database (100k requests/day, 5M row reads/day, 5 GB storage — see
  docs/FREE_TIER.md). Functions are orchestration-only: they dispatch
  workflows, poll run status and manage metadata.
* **GitHub Actions for production** — the engines already live on GitHub;
  hosted runners have FFmpeg/Python; artifacts provide free temporary storage
  for rendered videos. Rendering in Workers would be impossible (CPU/memory/
  duration limits) and expensive.
* **Vanilla JS SPA** — no build step to break, instant loads on tablets, and
  the whole UI is inspectable. Charts are hand-rolled SVG (no chart libraries).
* **D1 as job registry** — the dashboard, not the engines, is the authority on
  “what was published”, enabling cross-engine duplicate prevention.

## Data flow of one production run

1. User dispatches an engine (or the orchestrator does) →
   `POST /api/engines/:id/run`.
2. Backend validates: duplicate check (pre-dispatch), schedule state, config →
   creates `jobs` + `runs` rows → calls GitHub
   `POST /repos/{o}/{r}/actions/workflows/{wf}/dispatches`.
3. GitHub Actions runs the engine on a hosted runner (script → visuals →
   voiceover → render → [draft end] → upload).
4. `POST /api/sync/github` (manual button, or a scheduled cron once
   configured) pulls real run status via the workflow-runs API and updates the
   registry: `completed → needs-review`, `failed → failed` + failure reason.
5. Reviewer approves in the Content Queue → job becomes `scheduled`.
6. `POST /api/jobs/:id/publish` runs the publish gate (upload registry →
   review → lock → dedupe → daily cap) and dispatches the workflow's `publish`
   phase. The engine workflow performs the actual YouTube upload with the
   configured visibility.
7. Sync confirms the upload; the registry records the real YouTube video ID.

## Auth flow

* `ADMIN_PASSWORD_HASH` (PBKDF2, generated by `console/scripts/hash-password.cjs`)
  lives in a Pages secret. `POST /api/auth/login` verifies with WebCrypto
  PBKDF2 and sets a signed, stateless session cookie
  (`HMAC-SHA256(payload, SESSION_SECRET)`, 12 h, HttpOnly/Secure/SameSite).
* `console/functions/api/_middleware.js` rejects every `/api/*` request without
  a valid session, except `/api/health`, `/api/auth/login`, `/api/auth/logout`.

## Frontend structure

* `assets/js/app.js` — shell, hash router, session lifecycle.
* `assets/js/ui.js` — icons, formatters (IST), SVG charts, drawer/modal/toast.
* `assets/js/pages/*.js` — one module per page; all data via `assets/js/api.js`.
* Responsive: ≥1280 full rail layout · ≤1024 sidebar becomes a drawer ·
  ≤720 tables reflow into stacked cards (grid `data-col` labels) ·
  ≤480 single column. No hover-only controls anywhere.

## Backend structure (Pages Functions)

```
functions/api/
├── _middleware.js        session guard
├── _lib/                 util (auth, dedupe keys), db (D1), github, safeguards
├── auth/                 login · logout
├── session.js · health.js · overview.js
├── engines/              index · test-connection · [engine]/run|cancel|retry|schedule
├── jobs/                 index (list/create) · [id]/index · approve|reject|
│                         regenerate|schedule|publish
├── orchestrate/run.js    mode-aware dispatch
├── runs/                 index · [id]/index · [id]/retry
├── calendar.js · schedule.js · analytics.js · settings.js
└── sync/github.js        GitHub → registry synchroniser (+ Mode-1 fallback)
```

`dev/server.js` implements the same contract in-memory for local use and for
the automated test suite.
